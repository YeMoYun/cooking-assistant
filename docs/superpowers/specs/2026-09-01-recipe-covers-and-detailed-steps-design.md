# 食谱真实封面与详细步骤增强设计

日期：2026-09-01  
状态：已由用户确认

## 目标

在不改变现有食谱应用两大模块和总体计划的前提下，改进 10,520 道食谱的浏览与教程质量：

1. 食谱列表卡片显示与菜品匹配的真实食物照片。
2. 所有步骤从简短动作升级为可直接照做的文字教程。
3. 加热步骤必须包含火候或温度、操作时间范围和完成状态。
4. 非加热步骤必须包含预计耗时或静置时间，并明确无需开火。
5. 不在具体步骤中展示图片；步骤保持纯文字教程与结构化提示。

## 已确认的产品决策

- 图片策略采用“原图优先、联网搜索补齐”。
- 原始 MIRecipe 数据中，9,722 道食谱包含真实步骤照片，共 80,731 张。
- 原食谱有照片时，取最后一张有效步骤实拍图作为卡片成品封面。
- 其余约 800 道无图食谱，以“菜名 + 主要食材 + 成品图”自动联网搜索图片。
- 卡片采用文字叠加式设计：标题、总用时和难度位于图片底部的深色渐变层上。
- 详情页可沿用同一张封面，但步骤区域不展示图片。
- 步骤增强覆盖全部 10,520 道食谱。

## 方案选择

采用混合增强方案：

1. 优先保留原食谱事实和原始照片。
2. 通过确定性解析和烹饪规则补齐常见步骤信息。
3. 只有在原步骤含义过于模糊时，才调用已配置的 OpenAI 兼容大模型补写。
4. 对生成结果进行结构、食材引用和操作顺序校验后才写入正式目录。

未采用以下方案：

- 全部图片重新搜索：会降低图片与具体食谱的匹配度。
- 让大模型全量重写所有步骤：更容易改变原做法或编造食材。
- 只精修热门食谱：不能满足全目录覆盖要求。

## 数据结构

现有食谱模型已经支持本设计所需的字段：

- `cover.remoteUrl`：原始或搜索获得的封面源地址。
- `steps[].instruction`：保留并扩写后的自然语言操作说明。
- `steps[].durationSecondsMin` / `durationSecondsMax`：操作时间范围。
- `steps[].heatOrDevice`：火候、温度或使用的设备；非加热步骤填写“无需开火”。
- `steps[].completionCue`：完成状态，例如颜色、质地、气味、水分或中心熟度。
- `steps[].commonMistake`：影响口感的常见错误。
- `steps[].safetyRequirement`：飞溅、交叉污染、未熟肉类和高温油等安全提示。

增强完成后提升内容版本号。已有用户数据以稳定的食谱标识关联，不因重新导入而删除收藏、笔记、购物清单、模型配置或密钥。

## 图片处理架构

### 原图提取

转换 MIRecipe 源数据时，读取每道菜 `instructions[].imgLink` 中的有效 HTTPS 图片地址，选择最后一张有效图片作为成品封面。转换器保留图片来源信息并输出缺图清单。

### 缺图搜索

缺图补全器只处理缺图清单。搜索词由食谱标题、前 3 个主要食材和“成品图”组成。候选图片必须满足：

- HTTP 请求成功且内容类型为图片。
- 尺寸足以作为卡片封面。
- 搜索结果标题或上下文与菜名、主要食材具有匹配关系。
- 不能使用明显的原料图、包装图、菜单截图或无关菜品。

搜索完成后写入可重复执行的封面清单。无法可靠匹配的食谱进入失败报告，不静默配入无关图片；只要仍有未解决记录，封面补全任务就不能标记为完成，也不能把不完整清单提升为正式版本。

### 本地缓存

浏览器不直接长期依赖外部图片地址。服务端在图片首次请求时下载、验证并压缩为适合卡片的本地缓存文件；后续直接返回缓存。缓存键由食谱标识和源地址摘要组成，源地址变化时自动生成新缓存。

下载失败时按顺序处理：已有缓存、重新下载、重新搜索、最终占位与失败记录。外部响应必须限制超时、文件大小、重定向次数和允许的图片类型。

## 步骤增强规则

### 基本原则

- 不新增原食谱未声明的主要食材。
- 不删除原步骤中的操作事实。
- 不改变步骤顺序。
- 原文已有明确时间、温度或火候时，以原文为准。
- 时间使用范围，避免把灶具差异伪装成绝对精确值。
- 每个加热步骤同时提供时间和可观察的完成状态，用户不能只依赖计时器。

### 动作分类

- 清洗、切配、称量：填写预计耗时，`heatOrDevice` 为“无需开火”。
- 腌制、浸泡、醒发、冷却：填写静置时间与环境条件，`heatOrDevice` 为相应环境或设备。
- 炒、煎、炸：填写火力或油温、持续时间、翻动频率和颜色/质地变化。
- 煮、炖、卤：区分烧开阶段与维持阶段，填写火力转换、时间和汤汁/食材状态。
- 蒸：填写上汽条件、蒸制时间和熟度判断。
- 烤：填写预热温度、烤制温度、时间和上色/内部熟度。

### 生成流程

1. 解析原步骤中的动作、食材、显式时间、火候、设备和完成状态。
2. 根据烹饪动作、食材类别、切配形态和前后步骤应用规则库。
3. 将原操作和补充信息合成为自然、完整的 `instruction`。
4. 对仍缺关键字段或语义模糊的步骤调用已配置的大模型。
5. 通过食谱模式校验、食材一致性校验、步骤顺序校验和安全规则校验。
6. 不合格记录写入报告并保留原食谱，不用错误增强结果覆盖正式数据。

## 前端设计

### 食谱卡片

- 图片占据卡片主要视觉区域并使用 `object-fit: cover`。
- 标题、总用时和难度叠加在图片下部。
- 文字区域使用自下而上的深色渐变，保证浅色和复杂背景上的可读性。
- 图片加载失败时切换到服务端缓存重试或占位图，卡片布局不跳动。
- 保持现有一页多食谱的密集网格，不增加卡片高度来展示长摘要。

### 详情步骤

每个步骤包含：

- 连续步骤编号与简短动作标题。
- 一段可以直接照做的自然语言教程。
- 火候/设备、时间范围和完成状态三个主要提示。
- 需要时显示常见错误和安全提醒。
- 不显示步骤图片。

## 数据流

```text
MIRecipe 原始数据
  -> 转换并提取原图
  -> 缺图搜索与封面清单
  -> 步骤解析和烹饪规则增强
  -> 可选大模型补写模糊步骤
  -> 内容与安全校验
  -> 规范化 JSONL
  -> 以 replace 模式重新导入 SQLite
  -> API 返回本地封面地址和结构化步骤
  -> 卡片与详情页渲染
```

## 错误处理与可恢复性

- 所有批处理写入临时输出，完整校验通过后再替换正式目录。
- 图片搜索、下载和模型请求支持断点续跑，已成功记录不会重复处理。
- 图片失败、步骤增强失败和校验失败分别输出机器可读报告。
- 批处理失败不删除当前可用目录，应用仍可继续使用上一版本。
- 重新导入只替换食谱目录内容，不清理个人数据。

## 验收标准

- 10,520 道食谱均具有经过验证的非占位真实食物封面。
- 9,722 道原有图片的食谱使用原食谱实拍图。
- 其余食谱通过自动搜索补齐；中间出现的无法可靠匹配项必须列入失败清单并继续处理，最终验收时未解决数量为 0。
- 所有加热步骤都具有火候或温度、时间范围和完成状态。
- 所有非加热步骤都具有预计耗时或静置时间，并明确无需开火或对应环境。
- 增强结果不丢失原食材、不改变原步骤顺序。
- 卡片呈现真实照片并采用已确认的文字叠加样式。
- 详情步骤不出现图片。
- 类型检查、生产构建和内容完整性校验通过。
- 人工抽查炒、煎、炸、煮、蒸、烤和非加热步骤，不新增大规模自动化测试套件。

## 非目标

- 本阶段不为每个步骤增加图片。
- 本阶段不重新设计搜索筛选器、智能语音助手、购物清单或冰箱识别。
- 本阶段不处理商业发布、图片授权审核或线上 CDN 部署。
